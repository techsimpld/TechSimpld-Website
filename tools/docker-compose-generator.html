How to Structure Production-Safe Docker Compose Stacks

      

        On my 3-node Dell OptiPlex 9020 Proxmox VE cluster (proxmox01, proxmox02, and proxmox03), Docker hosts live inside dedicated VMs or unprivileged LXC containers on VLAN 100. The single biggest difference between a fragile weekend test stack and a home lab that survives reboots and upgrades is consistent directory layout and clean separation between configuration and secrets.
      


      
Step-by-Step Deployment Workflow

      
    
        
  1. Select your core services: Check the applications you want to deploy together, such as AdGuard Home, Uptime Kuma, Gotify, or CouchDB. Keep unrelated services in separate Compose directories so restarting one app does not disrupt your DNS or monitoring stack.
    2. 
        
  2. Standardize your base storage path: Setting a predictable root like /opt/homelab/data or ./data keeps every bind mount under one folder. When Proxmox Backup Server (PBS) or rsync runs nightly snapshots, backing up that single directory captures every database and config file.
    3. 
        
  3. Verify PUID and PGID ownership: Run id on your Linux host before starting containers. Matching PUID=1000 and PGID=1000 prevents containers from writing root-owned files that lock out your regular user during edits or backups.
    4. 
        
  4. Check for host port conflicts: Ubuntu hosts running systemd-resolved bind port 53 by default, which collides with Pi-hole and AdGuard Home. Override conflicting host ports in step 3 above, or disable the stub listener before running docker compose up -d.
    5. 
      


      
Security & Maintenance Rules of Thumb

      
    
        
  • Never commit secrets to YAML: Keep database passwords, API tokens, and tunnel keys inside .env and add .env to .gitignore. If you share or back up your docker-compose.yml, your credentials stay local.
    • 
        
  • Bind to localhost behind tunnels or reverse proxies: If a service is only accessed through a Cloudflare Zero Trust Tunnel or Nginx Proxy Manager on the same host, bind its port as 127.0.0.1:8080:8080 instead of 8080:8080 so it is not exposed on your LAN interface.
    • 
        
  • Avoid blind auto-updates on databases: Use a delayed updater like Arcane with version pinning rather than blindly pulling :latest on PostgreSQL or CouchDB containers, where a major version jump can require manual schema migration.
    • 
        
  • Use named user-defined bridge networks: Placing related containers on a dedicated bridge network (such as homelab_net) enables automatic Docker DNS resolution by container name, so Uptime Kuma can ping http://gotify:80 without hardcoded LAN IPs.
